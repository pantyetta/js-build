まず壊して見せる

この3行を、ビルドせずにブラウザで動かすと？

<script type="module">
  import { nanoid } from 'nanoid';
  console.log(nanoid());
</script>
Uncaught TypeError: Failed to resolve module specifier "nanoid".
Relative references must start with either "/", "./", or "../".

ライブラリは node_modules/ に入っている。
でもブラウザは node_modules という場所を知りません。

ライブデモ推奨。リポジトリの 00-no-bundler/ を npx serve . で開き、DevTools のコンソールにこのエラーを出す。ここで「毎日書いてるこの1行、実は誰かが解決してくれてる」と気づいてもらう。
問題の整理

素のブラウザにできないことが、そのままビルドツールの存在理由

  • パッケージ名を解決できない — 'nanoid' がどのファイルなのか、探す仕組みが無い
  • リクエストが爆発する — 1モジュール＝1リクエスト。実務規模なら数百〜数千本
  • JS 以外を import できない — CSS も画像も TypeScript も JSX も
  • 最適化してくれない — minify も、未使用コード削除も、古いブラウザ対応も

この4つを埋めるプログラム。それがビルドツールです。

4つのうち①だけが「バンドラが生まれた本当の理由」。②③④は後から乗ってきた仕事。次のパートでその歴史をやる、と繋ぐ。

script タグを、正しい順番に並べていた

<script src="jquery.js"></script>
<script src="utils.js"></script>   // jquery より後でないと動かない
<script src="app.js"></script>     // 順番を間違えると undefined
問題 1

依存の順番を人間が管理する

ファイルが増えるほど、正しい並びを知っている人が減っていく。

問題 2

全部がグローバル変数

どのファイルの誰が window.foo を書き換えたか追えない。

ファイルが10個を超えたあたりから破綻します。

古株のメンバーがいれば「これで消耗した記憶ありますよね」と振ると場が温まる。若手には「今も jQuery のプラグインとかで見かける形」と補足。

この図が今日の地図。以降のスライドで出てくる用語は全部この図のどこかを指している。時間があれば「みなさんが書いたことのある設定、どこに当たります？」と聞く。
いちばん多い混同

transpile と bundle は、別のものです

工程 ③

transpile（変換）

構文を別の構文に書き換える。TS→JS、ES2022→ES2015。
ファイルの数は変わらない。

工程 ①②

bundle（結合）

依存を辿って複数ファイルを束ねる。
ファイルの数が減る。

esbuild の設定で bundle: false にすると、import 文が そのまま出力に残ります。変換だけして、依存は辿っていない状態です。

用語意味混同しやすい相手
polyfill存在しないAPIを実装で埋める（Promise, fetch）transpile（あちらは構文の話）
tree shakingどこからも使われない export を落とすminify（あちらは縮めるだけ）
code splitting出力を複数ファイルに分ける。動的 import が起点bundle（逆向きの操作）
HMR状態を保ったまま変わったモジュールだけ差し替えlive reload（ページごと再読込）
tree shaking の補足：ESM の静的解析が前提。require() や import * as _ だと効かない。「バンドルが妙に大きい」の原因の大半がこれ。
設定ファイルの読み方

webpack で覚えるのは、5つのブロックだけ

ブロック役割5工程では
entryどこから依存グラフを辿り始めるか入口
outputどこに何という名前で吐くか⑤ Emit
module.rules拡張子ごとの変換方法（loader）③ Transform
pluginsビルド工程全体への介入全体
optimizationminify / tree shaking / chunk 分割④ Optimize

「webpack は設定が多い」と言われますが、mode: 'production' が 大半の既定値をまとめて面倒見てくれます。

実際の設定ファイルを画面に出しながら、この5つがどこにあるか指差すと早い。リポジトリの 03-webpack/webpack.config.js は①〜⑤の番号コメント入り。
山場 ① · 実物を読む

webpack の出力を開くと、こうなっている

// dist/main.js の冒頭（development ビルド＝minify なし）
var __webpack_modules__ = ({

  "./src/counter.js": ((module, exports, __webpack_require__) => { /* … */ }),

  "./src/utils.js":   ((module, exports, __webpack_require__) => { /* … */ })

});
  • 各モジュールが「関数」に包まれ、パスをキーにしたオブジェクトに登録されている
  • 関数の中なので、変数はグローバルに漏れない → script タグ時代の「問題2」の解決
ここは全員で読む。急がない。「キーが見覚えあるやつですよね」と、自分たちのファイルパスが文字列キーになっている点を指差す。
山場 ① · 実物を読む

そして、これが同じファイルの中にいます

function __webpack_require__(moduleId) {
  // キャッシュにあれば、それを返す
  const cached = __webpack_module_cache__[moduleId];
  if (cached !== undefined) return cached.exports;

  const module = __webpack_module_cache__[moduleId] = { id: moduleId, exports: {} };

  // 登録されている関数を実行し、exports を埋めさせる
  __webpack_modules__[moduleId](module, module.exports, __webpack_require__);

  return module.exports;
}

これは、Node の require を
ブラウザ用に再実装した関数です。

指差すポイント：①キャッシュを持つ ②初回だけ実行する ③ module.exports を返す。「これ、Node の require の挙動そのものですよね」で回収。
今日の芯 ① · 回収

これがバンドラの正体です

ブラウザに無いモジュールシステムを、
自前の関数として出力に埋め込んでいる。

  • webpack は 2012年生まれ。当時のブラウザには ESM が無かったので、こうするしかなかった
  • esbuild や Vite の出力（ESM形式）には、この関数はありません
  • ブラウザが ESM を理解するようになり、ランタイムを埋め込む必要が消えたから
  • webpack 5 も output.module: true で ESM 出力ができます
スライド07の伏線をここで回収。「バンドラ＝まとめる道具、という説明では、なぜ ESM 時代に形が変わったのか説明できない」と言うと差が立つ。
loader という考え方

なぜ CSS を「JS モジュールに変換」するのか

use: [ MiniCssExtractPlugin.loader, 'css-loader' ]
       ↑ ②番目に実行         ↑ ①番目に実行（配列の末尾から先頭へ）
  1. css-loader — CSS を読んで @import / url() を解決し、JS モジュールに変換
  2. MiniCssExtractPlugin.loader — それを .css ファイルとして書き出す
    （開発時は style-loader が <style> タグとして注入）

webpack にとって世界は全部 JS。loader は「JS 以外を JS に翻訳する通訳」です。
import './style.css' が最初は奇妙に見えるのは、この世界観のせい。

最頻出エラー Module parse failed: Unexpected token ＝「JS 以外を JS として解析して失敗」＝ 対応する loader が rules に無い。.vue .scss で出たらこれ、と教えると実務で効く。

実物を見る

Vite の dev サーバーは、import を書き換えている

自分が書いたコード

import { nanoid } from 'nanoid';

ブラウザに返ってきたコード（Network タブの Response）

import { nanoid } from '/node_modules/.vite/deps/nanoid.js?v=8f3a1c2b';
  • パッケージ名が実パスに書き換わっている — スライド03で落ちたやつの解決
  • 書き換え先は実在します：ls node_modules/.vite/deps/
  • 壊れたら rm -rf node_modules/.vite。Vite のトラブル対処、これで8割
できればライブで Network タブを開いて Response を見せる。スライド03のエラーと繋げると「あー！」が起きる。
2つの素朴な疑問

なぜ依存だけ事前バンドル？　なぜ本番はバンドル？

なぜ node_modules だけ

書き換え先が要るから

パッケージ名を実パスに直すには、その実パスが存在しないといけない。

なぜ node_modules だけ

リクエスト数を抑えるため

lodash のようなパッケージは内部が数百モジュール。そのまま配ると数百リクエスト。

なぜ本番はバンドル

実回線では成立しないから

非バンドル配信はローカルホストだから速いだけ。ネットワーク越しに数百リクエストは遅い。

開発と本番で別の道を通ります。 つまり「dev では動いたのに本番で壊れる」が起こり得る、Vite の既知のトレードオフ。
だからリリース前に vite preview で本番ビルドを確認します。

実務で効く注意点なので飛ばさない。「preview を通してからレビュー依頼」をチームのルールにしませんか、と提案に繋げてもいい。
注意 · 記事が古い

「Vite は本番で Rollup を使う」は、もう違います

$ npm ls rolldown
example-vite@
└─┬ vite@8.2.2
  └── rolldown@1.2.7

$ node -e "console.log(require('./node_modules/vite/package.json').dependencies)"
{ lightningcss, picomatch, postcss, rolldown, tinyglobby }
  • Rollup も esbuild も依存に居ません。バンドルは Rust 製の Rolldown（Oxc ベース）担当
  • CSS の処理は lightningcss
  • 検索で出てくる「dev は esbuild / 本番は Rollup」は当時は正しかった説明

この分野は動きが速い。
記事の日付を見る、手元で npm ls する。

同じ話がもう1つある：webpack 5.100 前後から .css は組み込み対応になり、css-loader 無しでもビルドが通る。今日の資料も来年には古くなる、と正直に言っておく。
