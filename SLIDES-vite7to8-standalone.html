1. Vite とは

  • フロントエンド開発用のビルドツール開発サーバーと本番ビルドの機能をまとめて提供する。読みは「ヴィート」（フランス語で「速い」）
  • 2020年に公開Vue.js の作者 Evan You 氏が開発。最新のメジャーバージョンは Vite 8（2026年3月）
  • 主要フレームワークで標準のツールVue・React・Svelte 等に対応し、Nuxt・SvelteKit・Astro 等では標準のビルドツールとなっている
コマンド用途
vite開発サーバーを起動する（ソースを編集しながら動作を確認）
vite build本番用のファイルを dist/ に出力する
vite preview出力した本番用のファイルをローカルで確認する
今回は主に vite build（本番ビルド）を扱う。開発サーバーとの違いは後半で説明する。

1. Vite は自分でビルドしていない

  • 実際のビルド処理は、バンドラや変換器といった下の層のツールが担当している
  • Vite はそれらを選んで組み合わせ、設定済みの状態で提供する
そのため、Vite のバージョンが上がると中のツールが丸ごと入れ替わる、ということが起こり得る。Vite 8 ではまさにそれが起きた。esbuild はバンドラにも変換器にもなれるため、両方の層に登場する。

1. Vite 7 → 8 で中のツールが入れ替わった

処理Vite 7Vite 8
本番のバンドルRollup（JS）Rolldown（Rust）
TypeScript・JSX の変換、JS の圧縮esbuild（Go）Oxc（Rust）
CSS の圧縮esbuild（Go）Lightning CSS（Rust）
開発時の依存パッケージの事前バンドルesbuild（Go）Rolldown（Rust）
  • JS 製と Go 製のツールの組み合わせから、Rust 製のツールに統一された
  • アプリのコードや設定ファイルの書き方は、基本的に変わらない
Rolldown は Rollup を Rust で作り直したもので、内部で Oxc を使っている。CSS の変換（PostCSS）は 7・8 とも変わらない。

1. 実際に測ってみた

Vite 7 Vite 8

CPU 8 コア。毎回 dist を削除した状態からビルド。

ツールを入れ替えただけで、なぜここまで速くなるのか。それを理解するには、ビルドが中で何をしているかを知る必要がある。

ここでは理由を言わず、問いとして残す。Vue が 4.8 倍にとどまっている点も覚えておいてほしい、と一言添える。答え合わせはパート3で行う。

2. そもそも、なぜビルドするのか

  • 他の言語を JavaScript にするTypeScript・JSX・.vue・CSS の import 等。ブラウザは JavaScript しか実行できない
  • モジュールを解決するimport 'nanoid' のようなパッケージ名の指定を、ブラウザは解決できない
  • 古い環境向けに構文を変換する新しい構文を、対象のブラウザが読める構文に書き換える
  • 配信を効率化するファイルをまとめてリクエスト数を減らし、使わないコードを削ってサイズを減らす

前の3つは「動かすための変換」、最後の1つは「速く届けるための最適化」にあたる。

IE11 のサポート終了以降、3つ目の比重は下がっている。

2. ブラウザは import を読めるのに、なぜバンドルするのか

  • パッケージ名を解決できない：'nanoid' がどのファイルかをブラウザは知らない → ファイルを特定する処理が必要
  • リクエストの待ち時間が積み重なる：ネットワーク越しでは遅くなる → ファイルをまとめる処理が必要
現在のブラウザは ES Modules（import / export）をそのまま読める。それでもバンドルする理由は、この2つに集約される。なお、Vite の開発サーバーはバンドルしていない（パート3で回収する）。

2. ビルドツールに共通する5つの工程

  • ①〜③ は import を見つけるたびに繰り返され、その結果「依存グラフ」ができあがる
  • Vite だけでなく、webpack や esbuild も同じ骨格で動いている
今回最も持ち帰ってほしい図。下の段は、Vite のプラグインが処理を差し込む場所（フック）の名前を示す。

2. 前提となる言葉：AST と依存グラフ

  • AST（抽象構文木）ソースコードを木構造のデータにしたもの。文字列のままでは変換も解析もできないため、まず構文解析（parse）して AST にする
  • 依存グラフどのファイルがどのファイルを import しているかの関係。AST から import を見つけ、その先を辿ることでできる
import { a } from './a.js'
  ↓ parse
ImportDeclaration { specifiers: [a], source: './a.js' }   ← 次に読むファイルが分かる

変換も tree shaking も圧縮も、すべて AST の上で行う。parse は負荷が大きく、パート3の答えにも関係する。

AST は Abstract Syntax Tree の略。

2-① Resolve：書かれた名前から実際のファイルを特定する

import { setupCounter } from './counter.js';   // 相対パス
import { nanoid }       from 'nanoid';         // パッケージ名（bare specifier）

// Resolve の結果
'./counter.js'  →  /project/src/counter.js
'nanoid'        →  /project/node_modules/nanoid/index.browser.js
  • nanoid は package.json の exports でブラウザ向けのファイルを指定しているため、index.browser.js に解決される
  • 実務では：Failed to resolve import はこの工程で発生する。@/ のような resolve.alias もこの工程に作用する
本番ビルドではソースの import 文を書き換えず、どのファイルかを確定させるだけにとどめる。最終的にはバンドルされ、import 文自体がなくなる。

2-② Load：ファイルの中身を読み込む

  • 普通のファイルmain.ts・style.css・App.vue 等をディスクから読む。この時点ではまだ JavaScript ではない
  • 仮想モジュールディスクに存在しないモジュール。ビルド日時やルート一覧などを、プラグインがその場で作って返す
  • 画像・フォント等読み込んだ後、次の工程で「URL を export する JavaScript」に変換される
  • 実務では：import routes from 'virtual:routes' のように、ファイルがないのに import できるのはこの仕組みによる
Nuxt 等のファイルベースルーティングも、この仕組みを応用している。

2-③ Transform：JavaScript に変換する

入力処理
.ts / .tsx型情報を取り除いて JavaScript にする
.jsxJSX を関数呼び出しに変換する
.vue / .svelte各フレームワークのプラグインが変換する
.cssJavaScript モジュールにする（開発時は <style> として注入、本番は ⑤ で .css に取り出す）
.json / 画像export default … の形にする
  • 変換したコードを parse して import を見つけ、① Resolve に戻る
  • 実務では：ビルドツールは型チェックをしない。型エラーがあってもビルドは通るため、tsc --noEmit を別に実行する必要がある
esbuild や Oxc が速い理由の1つは、型チェックをしないことにある。

2-④ Optimize：まとめて、削って、分ける

  • bundle（結合）：モジュールを1つのスコープにまとめ、名前がぶつかる変数をリネームする
  • tree shaking：依存グラフ全体を見て、どこからも使われていない export を削る
  • code splitting（分割）：動的 import（import()）の先や共通部分を別ファイルに分ける
  • minify（圧縮）：変数名を短くし、空白を消す。1ファイルの中で完結する処理
  • minify 以外は依存グラフ全体を見る必要があるため、モジュール数が増えるほど重くなる
  • 実務では：tree shaking は import / export の静的な解析を前提とする。require() や CommonJS のパッケージでは効かず、バンドルが大きくなる原因になる
tree shaking はグラフ全体を、minify は1ファイルを対象とする。見ている範囲が違う。

2-⑤ Emit：ファイルに書き出す

dist/
├─ index.html              ← script / link のパスを書き換え済み
└─ assets/
   ├─ index-Bx43ohxV.js     ← エントリ
   ├─ index-BBFHx35T.css    ← ③で JavaScript にした CSS を取り出したもの
   ├─ heavy-CuXC7Vo8.js     ← 動的 import で分割されたファイル
   └─ *.js.map              ← ソースマップ
  • index.html は、ハッシュ付きのファイル名を読み込むように書き換えられる
  • 実務では：ハッシュは中身から計算されるため、中身が変わればファイル名も変わる。そのためブラウザのキャッシュを長く設定しても問題が起きない
ソースマップは、圧縮後のコードの位置と元のコードの位置を対応づけるもので、本番のエラー調査で使う。ここでパート2は終わり。「では、この5工程の視点で Vite 8 を見直してみる」とつなぐ。

3. Vite 7 → 8 の変化を5工程で見直す

工程Vite 7Vite 8
①② Resolve / Load（依存グラフを作る）Rollup（JS）Rolldown（Rust）
③ Transform（TS / JSX）esbuild（Go）Oxc（Rust）
④ Optimize（bundle / tree shaking / split）Rollup（JS）Rolldown（Rust）
④ minify（JS / CSS）esbuild / esbuildOxc / Lightning CSS
⑤ EmitRollup（JS）Rolldown（Rust）
  • 工程そのものは何も変わっていない。各工程を実行するツールだけが入れ替わった
  • では、なぜツールを入れ替えると速くなるのか。理由は大きく2つある
パート1で見た表を、工程の単位で並べ直した。

3. 速くなった理由 1：①〜③ を並列に処理できる

  • ①〜③ はファイルごとに独立した処理ファイルの特定・読み込み・変換を繰り返すだけで、ファイル同士がお互いを待つ必要がない
  • Vite 7（Rollup）：JavaScript で、基本1スレッド約 6,900 個のファイルを、1本のスレッドで順番に処理していた
  • Vite 8（Rolldown）：Rust で、複数スレッドファイルごとの処理を、CPU の複数のコアで同時に進める

工程の性質が分かっていれば、どこが並列化で速くなるかが見えてくる。

測定には 8 コアのマシンを使った。④ の tree shaking などはグラフ全体を見るため、①〜③ ほど単純には並列化できない。

3. 速くなった理由 2：重い parse を何度もしなくなった

Vite 7 では担当ツールが替わるたびにコードを文字列に戻し、受け取った側がもう一度 parse していた（簡略化した図）。

拡張子が .js のファイルは Vite 7 でも esbuild の変換を通らないため、parse は1回少ない。また minify はファイル出力の後にかけるため、Vite 8 でもそこで再度 parse する。要点として、ファイルごとの parse の重複と、言語をまたぐときのコピーがなくなった。

3. Vue の構成が 4.8 倍にとどまった理由

  • JavaScript だけの構成：①〜⑤ が Rust の中で完結するすべてを Rolldown / Oxc が処理するため、並列化と parse の共有の効果がすべて出る
  • Vue の構成：③ Transform で JavaScript 製のプラグインを呼ぶ.vue の変換は @vitejs/plugin-vue（JavaScript）が担当する。Rust から JavaScript に文字列で渡し、JavaScript 側でもう一度 parse し、1スレッドで処理する

工程が分かっていれば、どこが速くなり、どこが速くならないかを予想できる。

JavaScript 製のプラグインで大量のファイルを変換している構成ほど、Vite 8 の効果は小さくなる。ファイル数が少ない分、起動などの固定の時間の割合が大きいことも影響している可能性がある。

3. 開発サーバーは5工程の一部しか使っていない

工程開発サーバー（vite）本番ビルド（vite build）
①②③ブラウザから要求されたファイルだけすべてのファイル
④ Optimizeしないbundle / tree shaking / splitting / minify
⑤ Emitしない（HTTP で直接返す）dist/ に書き出す
  • 開発サーバーはバンドルしない：手元のマシンならリクエストが多くても遅くならないため、まとめる必要がない。だから起動が速い（パート2の問いの答え）
  • 本番ビルドは全ファイルに5工程をかける：ファイル数に比例して時間がかかる。冒頭の 29 秒はこちらで発生している
例外として、node_modules のパッケージだけは開発時も起動時にまとめてバンドルする（node_modules/.vite/deps）。パッケージの中のファイルをそのまま配ると、手元でもリクエストが多くなりすぎてしまう。

3. Vite 8 でも vite preview での確認は必要

  • Vite 7 まで：開発時と本番で使うツールが違っていた開発時の事前バンドルは esbuild、本番のバンドルは Rollup
  • Vite 8：開発時も本番も Rolldown / Oxc に統一されたツールの違いによる挙動の差は小さくなった
  • ただし、④⑤ を通るかどうかの違いは残る開発時は、圧縮や tree shaking を通っていないコードが動いている

リリース前には、今後も vite preview で本番用のファイルの動作を確認する必要がある。

「開発と本番が同じになった」とは言えない。5工程で見れば、何が揃い、何が残ったかを分けて説明できる。

4. まとめ

  1. Vite 8 は、中のツールを Rust 製に統一して大幅に速くなったJavaScript だけの構成で 29 秒 → 0.5 秒。JavaScript 製のプラグインを通る部分は速くなりにくい
  2. JavaScript のビルドは5工程でできているResolve / Load / Transform を繰り返して依存グラフを作り、Optimize / Emit でまとめて出力する
  3. 速くなった理由は、工程の性質で説明できるファイルごとに独立した ①〜③ を並列化し、重い parse の重複をなくした

5工程を知っていれば、ツールが変わっても「何が変わったのか」を自分で読み解ける。

新しいビルドツールが出てきたら、まず5工程のどこを誰が担当しているかを見るとよい。

補足：よくある質問

質問回答
型チェックは誰がしているのかesbuild も Oxc も型を取り除くだけで、型チェックはしない。CI などで tsc --noEmit を別に実行する。
ビルド結果はキャッシュされるのかvite build はビルド結果をキャッシュしない。今回の測定も、毎回 dist を削除して実行している。
